# 現地限定投稿：ローカル実装・公開前手順

このフォルダーのSQLは**提案・本番未適用**です。既存の未承認の投稿管理SQLとは別物であり、まとめて適用しません。

## 動作

- 日常投稿：ホームの「今いる場所を宝物にする」。最初のGPSで投稿地点を固定します。冒険検索は不要です。
- 冒険投稿：現在のUIDで通常冒険のGPS到着が完了した場合に、到着画面から目的地を固定して投稿できます。UID不明の旧到着記録を他アカウントへ帰属させません。デート冒険の履歴・報酬処理は変更していません。日常投稿の入口は利用できます。
- 両方とも登録開始時と保存直前に、50m以内の精度・30秒以内の測位・固定地点から100m以内を確認します。写真処理後にも再測位します。
- 写真・文章・カテゴリーを残してGPSだけ再取得できます。画面移動後の遅いGPS応答は保存へ進めません。
- 投稿だけではEXP、到着記録、個人図鑑、たからん育成を書き換えません。

## 保存とプライバシー

ブラウザーの `createTreasure` はテーブルへ直接INSERTしません。専用APIがGoogleの認証済みユーザーをSupabase Authで確認し、GPSと投稿地点を検証します。ブラウザーのmode/到着フラグだけで保存を許可しません。既存の冒険到着記録は端末側にあるため、サーバーは過去の冒険達成自体を認証する仕組みではありません。サーバーが必須条件とするのは、今回提出された新しい測位の整合性です。日常投稿も許可されるため、冒険検索は保存権限の条件ではありません。

サーバーが発行する256bit乱数は60秒有効で、UID・投稿内容のハッシュ・リクエストIDに結び付きます。DBにはそのハッシュのみを保存します。行ロックを使った1トランザクションで登録と使用済み化を行い、同じリクエスト・内容の再送には既存の登録IDを返します。別UID・別内容・別トークンでは使用できません。

保存結果が不明な場合は、入力を固定し写真を消さず再確認します。再読み込みにも備え、新規のUID別localStorageキー `machiPendingOnsitePost.v1:<UID>` に投稿内容・写真参照・リクエストIDだけを保存します。これは投稿しようとした公開情報の控えです。認証トークン・確認トークン・測位日時・精度・移動履歴は保存しません。成功確認後にこの控えだけを除去します。壊れた控えを勝手に上書きしません。既存の図鑑・EXP・名前のキーは変更しません。アップロード前の写真ファイルそのものはページ再読み込みでは復元できません。

GPSはブラウザーから申告されるため、偽装を完全には防げません。これは端末認証による現地証明ではありません。診断やAPIの通常ログへトークン・座標・文章を出しません。

## 必要なDB変更：01-proposed.sql

1. `onsite_post_requests`：UID、リクエストID、投稿内容ハッシュ、確認トークンハッシュ、有効期限、登録ID。一般ロールから読み書き・RPC実行を許可しません。
2. `onsite_post_photos`：今回以降の登録と写真オブジェクトの参照を結び付けます。外部キーにより、保存済み写真を後片付けと競合して消さない設計です。既存27件等への遡及登録はしません。
3. 投稿用RPC2本と検証関数：実行はサーバー用ロールに限定。登録・一回限り処理は原子的に行います。
4. `treasures` のanon・authenticatedの直接INSERT権限を取り消します。既存のSELECT・報酬関数・評価関数は変更しません。継承権限が残る場合は全体を中止します。
5. Storageのauthenticatedロールに本人UIDのパスとowner_idが一致する新画像のみのアップロード・参照を許可。削除は本人の未参照画像のみ。原本の移行・削除、既存の所有者の推測補完はしません。

SQLには3秒のロック待ち、15秒の処理期限と想定外状態の停止条件があります。過去の `create_my_treasure` RPCが存在する場合などは、自動的に権限を変更せず停止します。現在の本番の列型・権限・ポリシーとの再照合が適用の必須条件です。Storage objects.idはuuid、owner_idはUID文字列である前提です。
