# ローカル検索の確認手順

## 起動
1. プロジェクトのターミナルで、実行中の開発サーバーを Ctrl+C で停止します。
2. npm run dev を実行します。表示された Local のURLをブラウザで開きます。
3. 同じURLの末尾に /api/diagnostics を付けて開きます。environment が local、overpass が local-handler ならローカルAPIです。404なら古いサーバーや preview を開いていないか確認してください。
4. 元の画面を再読み込みします。保存済みのログイン・冒険記録を消す必要はありません。

## 無料での画面確認
ローカルの徒歩距離APIは課金防止のため明示的に無効です。固定距離検索で経路確認が必要になると503が返り、到達候補が確認できない場合があります。これはOverpassの候補0件とは別です。実距離に見せかけた模擬データは画面に返しません。本番の徒歩距離処理は変更していません。

画面から無料のOverpass接続を確認するときは、検証用に自分で距離「？km」を選択してください。この条件は徒歩距離APIを使いません。アプリが距離・カテゴリ・料理ジャンルを自動変更することはありません。冒険開始後の距離取得もローカルでは無効なので、今回の確認は目的地検索までにしてください。

F12で開発者ツールを開き、Consoleで overpass-client を検索します。success は通信成功、count: 0 は正常な空結果、failure / timeout は障害、cache-hit は期限内の再利用です。APIを実行するターミナルでは overpass-api に接続先・HTTP状態・候補件数が出ます。Networkの /api/overpass 応答ヘッダー X-Machi-API-Environment: local でも確認できます。

0件は30秒、候補ありは5分でキャッシュ期限が切れます。失敗は保存しません。期限前の正常な空結果を直ちに再取得したい場合はページを再読み込みしてください。個人記録のlocalStorageを削除しないでください。

## 再現テスト
npm test で無料の模擬応答テストを実行します。通信障害→同条件の成功、真の0件、空結果の期限切れ、部分応答、タイムアウト、ローカルHTTP接続、Routes呼び出し遮断を確認します。Google Routes実呼び出しはありません。

本番はVercelの /api/overpass、開発は同じTypeScriptハンドラーをVite内で実行します。本番への開発プロキシはありません。npm run preview は静的ビルドのプレビューでありAPI検証用ではありません。設定ファイルは各npmスクリプトで vite.config.ts を明示しています。

## 診断の扱い
normal-search の candidate_limit_reached は16件の確認上限、service_failure はサービス障害、no_matching_candidates は確認対象に適合候補がないことを示します。候補数と未確認数も合わせて確認してください。上限や抽選ロジックは変更していません。
今回の検索診断は座標・店舗名・クエリ・認証情報・応答本文を出力せず、外部送信や永続保存もしません。Networkの要求本文には検索に必要な座標が含まれるため、HARやConsole全体をそのまま共有せず、診断行の件数・状態だけ共有してください。

スマートフォンからLANのHTTPアドレスで開くと位置情報やOAuthの制約があります。今回はPCのlocalhostで接続を確認してください。スマホでのGPS・Googleログインを含む確認には、別途許可済みHTTPS開発環境とOAuthリダイレクト設定が必要です。


## 検索安定化工程の更新
- 開発サーバーは5173固定です。使用中なら5174へ移らず終了します。既に起動しているターミナルを確認し、Ctrl+Cで停止してから起動し直してください。終了前の再確認で5173・5174の両方の待ち受けを確認しました。両方の開発ターミナルでCtrl+Cを押し、1つのターミナルだけでnpm run devを実行してください。前工程の確認用5197は停止済みです。
- 同一クエリの進行中通信を共有します。ブラウザタブ内で同時2件、待機4件までです。全ユーザーを横断する制限ではありません。多数のタブを同時に開いて検索しないでください。
- 有効キャッシュは通信より先に利用します。異なるGPS座標・半径・カテゴリ・料理条件のクエリには流用しません。期限切れの結果を障害時に延命することはありません。
- コイン画面から進む際、現在地が未取得、復元した出発地点しかない、または取得後5分を超えた場合は再取得します。失敗すると選んだ条件を保持してその画面に留まります。許可を直して同じボタンを押せば再取得できます。ページ更新で過去の出発地点を新しいGPSとして扱いません。到着時のGPS判定は別処理のままです。
- ローカルの固定距離検索では徒歩距離APIを無効にしているため、walkingの案内は想定される動作です。無料の実接続確認は自分で？kmを選びます。アプリが条件を勝手に変更することはありません。
- Consoleの normal-search stopped のreason: overpass=施設検索障害、empty=利用可能候補0件、distance=距離/経路条件不適合、limit=確認上限、walking=徒歩距離確認失敗、treasures=宝物読込障害。現在地失敗はコイン画面に案内が出ます。
- ターミナルのoverpass-apiでは、個人情報を含まないクエリ形状（node/way/relation節数、名前正規表現の有無、料理タグの有無）、所要時間とHTTP状態を確認できます。正規表現本文や座標は記録しません。

## 今回のクエリ調査と限界
カフェは1節、公園はnode+way、景色は2節、おまかせは選ばれたカテゴリ1種類を検索します。和食・スイーツは複数タグと名前正規表現のため相対的に複雑です。10km指定の初期検索は既存仕様の11km半径で、地域密度によって負荷が増えます。どのクエリが500/504の原因だったかは、以前の記録だけでは特定できません。公開サーバーの混雑でも失敗するため、新しい診断で切り分けます。

今回は既存UIが必要とする[name]をサーバー側で絞り、名前のないデータ転送を減らしました。node/way/relationの一括拡大、料理条件の削減、半径の縮小は行っていません。type+idによる重複除去と不正座標・空白名の除外は、徒歩距離確認より前に行います。同じ場所のnodeとwayを推測で統合することはありません。

既存のOverpassクエリ実行制限12秒、接続先ごとの通信制限25秒、クライアント55秒を維持しています。むやみに時間や再試行回数を増やしません。公開サーバーは成功率保証のある無料サービスではなく、利用増加時は継続的な負荷監視と構成の再検討が必要です。
参考: https://dev.overpass-api.de/overpass-doc/en/preface/commons.html


## 接続先改善工程（2026-10-12）
第1候補はVK Mapsの全世界対応公開Overpass、第2候補はPrivate.coffeeです。旧kumiとスイス限定サーバー、deへの自動接続は使いません。利用条件・運営元・商用利用の確認範囲はdocs/overpass-providers.mdを参照してください。

1. 実行中の開発ターミナルをCtrl+Cで停止し、1つだけでnpm run devを実行します。
2. /api/diagnosticsのenvironment: localを確認します。
3. 自分で現在地を取得し、距離？km・カテゴリを選び、コイン→ガチャ→目的地へ進みます。GPS許可を拒否した場合はコイン画面で再取得してください。
4. Consoleのoverpass-clientにprovider: vk-mapsまたはprivate-coffee、status: success、countが出ます。APIのターミナルにはHTTP状態と所要時間が出ます。
5. normal-search succeededのsource: overpassなら一般施設、treasureなら登録宝物です。候補がない場合はnormal-search stoppedのreasonを確認します。施設名・座標を診断に含めません。
6. 同じ条件を5分以内に再抽選するとcache-hitで候補を再利用します。再抽選自体は行われます。
7. 429/403/406を受けた場合は別サーバーで回避せず、最低30秒、Retry-Afterが長ければその期間待ちます。自動的な無制限再試行はありません。

今回の画面検証は、別ポート・別ブラウザ保存領域で東京駅の公開GPSだけを模擬し、Overpassは実通信しました。GPS模擬の検証用起動設定は作業用フォルダにあり、製品コードや本番ビルドには含めていません。利用者の実GPS・保存記録はそのままです。
